# ChurchOS H5 需求共创平台设计规范

日期：2026-07-15
状态：已确认，待实施

## 1. 目标与范围

本项目在现有 Node.js、Express、原生 HTML/CSS/JavaScript 原型上，完成一套可在手机和桌面浏览器中操作的 ChurchOS 需求共创网站。交付重点是完整、连贯、可演示的产品体验，而不是只还原几张静态设计图。

首版覆盖以下用户流程：

1. 游客浏览 ChurchOS 共创计划首页。
2. 游客登录或注册为同工用户。
3. 用户进入需求广场，按分类和热度浏览需求。
4. 用户提交需求、查看相似需求、上传图片或模拟语音转写。
5. 用户点赞、取消点赞、评论、回复和查看助力同工。
6. 用户查看合并状态、补充细节、发起拆分申诉。
7. 用户复制分享链接并生成或下载分享海报。
8. 管理员查看数据分析、处理申诉、管理倒计时并导出报告。

真实 AI、邮件、短信、精确地理定位和第三方认证不属于首版生产集成范围。这些能力使用界面完整、返回稳定、后续可替换的模拟服务实现。

## 2. 技术方案

采用现有技术栈，不进行 React 或其他框架迁移：

- 前端：HTML5、CSS3、原生 JavaScript ES6。
- 后端：Node.js、Express。
- 数据：`db/` 目录中的 JSON 文件。
- 文件上传：Multer。
- 图标：使用 Lucide 图标库，保留必要的品牌十字标识。

保留现有 REST API 方向，并对前端职责进行拆分。页面继续采用单页应用结构，通过视图状态切换首页、广场和后台，通过弹窗呈现登录、注册、提交、详情和分享流程。

## 3. 前端模块边界

前端按职责拆分，避免所有行为继续集中在一个脚本中：

- `app-shell`：应用启动、全局状态、页面切换、顶部导航和 Toast。
- `auth`：登录、注册、退出、浏览器本地会话和权限拦截。
- `landing`：首页文案、倒计时、语言选择器和底部快捷抽屉。
- `wishes`：广场列表、筛选、排序、提交、查重、点赞和需求详情。
- `comments`：评论列表、二级回复和评论翻译状态。
- `sharing`：链接复制、分享弹窗、二维码和海报生成。
- `notifications`：通知拉取、未读数、清除和跳转。
- `admin`：分析概览、申诉处理、倒计时设置、导出和模拟邮件反馈。
- `api-client`：统一请求、错误转换、加载状态和认证信息注入。
- `i18n`：界面语言字典和内容翻译展示状态。

模块通过明确的函数和事件协作，不直接修改彼此的内部状态。

## 4. 页面与交互设计

### 4.1 H5 首页

首页是产品第一屏，直接展示 ChurchOS 品牌、共创计划、核心事工板块和参与价值。顶部提供语言选择、通知和登录后的用户信息。

底部快捷抽屉包含“注册/登录”“查看需求”“我要提需求”“我要分享”四个入口。初始状态展开；用户发生滚动后自动折叠，只保留固定高度的手柄；用户可手动重新展开或收起。抽屉尺寸固定，状态切换不能造成正文布局跳动。

管理员开启活动截止时间时，首页展示倒计时。截止后，浏览仍可用，但提交、点赞和评论入口进入禁用状态并说明原因。

### 4.2 登录与注册

鉴权弹窗默认显示登录页。注册页包含邮箱、密码、展示姓名、头像、教会名称、地区和服侍职务。教会名称支持输入联想；地区使用模拟定位结果预填，用户可修改。

注册成功后显示成功提示，自动切回登录页并预填邮箱。登录成功后关闭弹窗，顶部展示用户头像和昵称，受限操作继续执行或引导用户重新触发。

### 4.3 需求广场

广场使用适合手机扫描的单列卡片，桌面端扩展为多列。顶部提供横向分类标签、热度或时间排序以及提交入口。

每张卡片显示作者、所属教会、职务、标题、摘要、状态、点赞数、评论数和最近助力头像。点击卡片主体打开详情；点击点赞器直接点赞或取消点赞。未登录用户执行写操作时打开登录弹窗。

### 4.4 提交与查重

提交表单包含分类、标题、详细描述、1 至 3 张图片和可选语音输入。标题最长 30 字，描述至少 10 字。

用户输入标题后进行防抖查重。匹配结果以建议列表展示，可直接前往相似需求点赞或查看详情。模拟语音转写返回文字与置信度；低置信度结果明确提示用户修改，不自动覆盖已有内容。

### 4.5 需求详情与共创

详情保留原始需求正文和附件，独立展示协同补充内容、管理员置顶回复、合并原因和申诉状态。评论支持二级回复。翻译按钮只切换当前内容的译文展示，不破坏原文。

已合并需求显示目标需求链接。原作者可发起拆分申诉；非原作者不显示该操作。采纳或完成状态使用清晰标签，不仅依赖颜色表达。

### 4.6 分享

分享弹窗提供链接复制、二维码和 2:3 海报预览。海报通过 Canvas 在浏览器生成，包含 ChurchOS 品牌、共创计划标题、简短价值说明和二维码。下载失败时保留预览并提供再次尝试。

### 4.7 管理后台

管理员后台在桌面端使用侧栏和工作区，在手机端转为顶部标签。功能包括：

- 需求和参与者统计。
- 模拟 AI 痛点聚类与优先级建议。
- 合并申诉审批。
- 倒计时和活动截止设置。
- Markdown 与 CSV/Excel 兼容格式导出。
- 分享链接、二维码和海报管理。
- 模拟群发反馈邮件及进度展示。

## 5. 视觉系统

视觉参考 `docs/ui_spec.md` 和 `public/images/` 下的高保真稿，采用克制的深色玻璃界面：

- 背景以深灰、炭黑和低饱和蓝灰为主。
- 青色用于主行动、选中状态和关键数据。
- 暖金或橙色用于倒计时、采纳和提醒状态。
- 红色仅用于错误、截止和破坏性操作。
- 文本保持高对比度，正文不使用过细字重。
- 卡片圆角不超过 8px；弹窗可使用略大的圆角，但不嵌套装饰性卡片。
- 按钮优先使用图标或图标加文字，提供悬停提示和可见焦点状态。
- 移动端主要控制区域满足至少 44px 的触控高度。

所有固定格式组件使用稳定尺寸或响应式约束，避免按钮文字、加载状态和数量变化造成布局位移。

## 6. 数据流与权限

浏览器启动后读取本地会话并请求用户信息。公开页面和需求列表无需登录；写操作通过统一鉴权守卫检查用户状态。

登录成功后保存最小会话信息，并由 API 客户端为请求注入身份标识。管理员接口同时验证登录和管理员权限。前端隐藏入口只是体验优化，后端权限校验是最终边界。

所有需求、评论、点赞、通知和活动设置写入 JSON 数据库。写入操作必须经过字段校验，并返回前端可直接展示的错误信息。

## 7. 错误与空状态

每个异步区域包含加载、成功、空数据和失败状态：

- 网络失败：显示可重试提示，不清空用户表单。
- 表单错误：在对应字段附近说明，并在顶部汇总首个错误。
- 权限不足：说明需要登录或管理员身份，不显示笼统报错。
- 空广场：显示提交首条需求的入口。
- 无搜索结果：保留筛选条件并提供重置操作。
- 上传失败：指出失败文件，已成功选择的文件继续保留。
- 截止状态：所有被禁用的参与操作使用同一原因说明。

## 8. 响应式与可访问性

主要验证视口：375x812、390x844、430x932、768x1024、1440x900。

页面支持键盘操作、可见焦点、语义化标签、弹窗焦点限制、Escape 关闭和背景滚动锁定。图标按钮包含可访问名称，状态不只通过颜色表达。长中文、英文邮箱、教会名称和翻译文本必须正确换行且不溢出容器。

## 9. 测试与验收

### 9.1 自动验证

- API 的注册、登录、需求、点赞、评论、申诉和管理员核心路径。
- 前端关键纯函数：筛选排序、倒计时、表单校验、状态映射和翻译切换。
- 启动检查和静态资源访问。

### 9.2 浏览器流程验证

1. 游客打开首页并滚动，底部抽屉自动折叠。
2. 游客点击受限操作，被引导登录。
3. 用户注册成功后返回登录并预填邮箱。
4. 用户登录、提交需求、查看查重建议、点赞和评论。
5. 用户打开详情、查看翻译和合并状态。
6. 用户复制链接、生成并下载分享海报。
7. 管理员登录、查看分析、处理申诉、配置倒计时并导出数据。

### 9.3 视觉验证

在手机和桌面视口使用浏览器截图检查：首屏品牌信号、文本换行、弹窗高度、底部抽屉遮挡、卡片密度、后台布局和分享海报渲染。页面不得出现横向溢出、交互控件重叠或不可读文本。

## 10. 明确不做

首版不接入真实大模型、真实邮件供应商、短信服务、OAuth、支付、生产级数据库、生产级密码存储或全球教会权威数据源。现有明文测试密码仅限本地演示数据，并在界面和文档中明确为演示环境。

这些能力通过模块接口隔离，未来可以替换，而不需要重写页面流程。
