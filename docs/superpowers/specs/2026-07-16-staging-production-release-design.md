# ChurchOS 测试环境与正式发布设计

## 目标

建立一套“先测试、后发布”的工作流。以后所有功能和 UI 调整先进入测试环境，不影响 `churchosapp.org` 正式站。只有站长确认发布后，才把测试通过的代码发布到正式站。

## 环境划分

项目使用两个 Render Web Service：

- 测试环境：连接同一个 Supabase 项目里的 `staging_` 数据表，用于开发、预览、验收。
- 正式环境：连接正式数据表，用于公开访问和真实用户提交。

两个环境可以使用同一份代码，但通过环境变量决定读取哪一套表。

## Supabase 数据隔离

不新建 Supabase 项目。当前正式表保持不变，测试环境使用同一个 Supabase 项目中的同结构测试表。

正式表示例：

- `users`
- `wishes`
- `comments`
- `settings`
- `notifications`
- `email_logs`

测试表示例：

- `staging_users`
- `staging_wishes`
- `staging_comments`
- `staging_settings`
- `staging_notifications`
- `staging_email_logs`

后端数据库层新增一个表名前缀配置，例如：

- 正式环境：表名前缀为空
- 测试环境：表名前缀为 `staging_`

所有读写都通过统一数据库适配层映射表名，业务代码继续使用逻辑表名，避免每个接口手动判断环境。

## 发布流程

开发和测试流程：

1. 我在开发分支提交修改。
2. Render 测试服务自动部署。
3. 你打开测试网址验收功能、UI、文案和流程。
4. 如果需要调整，继续只改测试环境。

正式发布流程：

1. 你明确说“确认发布”。
2. 我把测试通过的代码合并到正式发布分支。
3. Render 正式服务自动部署到 `churchosapp.org`。
4. 正式环境仍然读取正式表，不读取 `staging_` 测试表。

## 数据清理策略

测试环境可以安全清理测试数据，因为它只操作 `staging_` 表。

正式环境的“首次上线清空测试数据”仍只允许执行一次。正式站上线后，不再提供反复清空正式数据的能力。

## 后台首页内容发布关系

后台首页内容的“草稿 / 预览 / 发布”仍然只作用于当前环境：

- 在测试站编辑，只影响 `staging_settings`。
- 在正式站编辑，只影响正式 `settings`。

测试站发布首页内容不会自动覆盖正式站首页内容。正式网站更新依赖代码发布；如果未来需要把测试站后台文案同步到正式站，可另做“内容同步”工具。

## 风险与防护

- 风险：某个接口绕过统一数据库适配层，直接访问真实表。
  - 防护：后端只暴露逻辑表名，表名前缀在数据库适配层统一处理，并增加测试覆盖。

- 风险：测试环境误用正式表。
  - 防护：Render 测试服务必须配置 `CHURCHOS_TABLE_PREFIX=staging_`；正式服务保持为空。

- 风险：测试表结构和正式表结构不一致。
  - 防护：提供一份 Supabase SQL，用来一次性创建与正式表同结构的 `staging_` 表。

## 验收标准

- 测试服务和正式服务可以连接同一个 Supabase 项目。
- 测试服务只读写 `staging_` 表。
- 正式服务只读写正式表。
- 测试站提交需求、注册用户、后台编辑首页内容，不影响正式站。
- 正式站数据不会出现在测试站列表、统计、导出或后台中。
- 一键清空测试数据只清空当前环境对应的数据表。
